MVVM Architecture Summary

For this assignment, we took the Course Tracker from Assignment 2 and refactored it into an MVVM architecture with two screens. In Assignment 2, CourseTrackerScreen was the parent composable that held all the state with rememberSaveable, and it also had the rules for enrolling, toggling prerequisites and the override inside its callbacks. That worked, but it meant one composable was doing two jobs at the same time: drawing the UI and deciding the business logic.

Now, all of that lives in CourseViewModel. The four values that used to be separate rememberSaveable variables (searchQuery, overridePrereqs, enrolledCourseIds and satisfiedPrereqIds) are now fields of a single immutable data class, CourseUiState, which the ViewModel keeps in a private MutableStateFlow and exposes as a read-only StateFlow. The screens can't change the state directly; they can only call the public functions onSearchQueryChanged, togglePrerequisiteBypass, togglePrerequisiteStatus and toggleCourseEnrollment. Every change is done with update and copy, so the screen always receives a complete new snapshot instead of four values that could change at different times. The values that are calculated, like the visible courses, the enrolled courses and the total credits, are also part of CourseUiState, and since they are calculated from the fields every time a new copy is made, they can't get out of sync.

This improved the architecture in a few ways. The first one is a clear separation of responsibilities: the composables only display the state and send events, and the ViewModel decides what those events actually do. For example, the rule that a course can only be enrolled if its prerequisite is satisfied or overridden is now checked inside toggleCourseEnrollment, not only by disabling the button, so the rule doesn't depend on the UI. The second one is lifecycle: a ViewModel survives configuration changes like rotating the phone, so we no longer need rememberSaveable for the enrollment data. The third one, and probably the most important one for this assignment, is that the state can be shared between screens. The ViewModel is created once in CourseAppNavigation, outside the NavHost, so the DashboardScreen and the CourseDetailScreen both get the same instance. When the user enrolls in a course from the detail screen and goes back, the dashboard already shows the updated credit total, which would have been a lot harder with state that lived inside one composable.

Additionally, we split each screen into two parts: DashboardScreen and CourseDetailScreen collect the StateFlow with collectAsState, and DashboardContent and CourseDetailContent are stateless and only receive a CourseUiState and callbacks. This kept the same state hoisting idea from Assignment 2, and it also made the previews easier, since we can pass a fake state without creating a ViewModel.

Finally, the rest of the refactor built on top of this. The course list is now a LazyColumn with key = { it.id }, so only the visible cards are composed, and when the search filters the list, Compose knows which card is which. Each card loads the instructor picture asynchronously with Coil's AsyncImage, with a placeholder while it loads and the same placeholder if it fails. And the app now uses a Material 3 Scaffold with a TopAppBar on both screens, an enrollment badge on the dashboard, and a back button on the detail screen that calls popBackStack.
